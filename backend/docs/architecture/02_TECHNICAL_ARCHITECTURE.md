## 2. Architecture Principles

### 2.1 Frontend Never Calls Payment Gateways Directly
All payment operations go through the backend API. The frontend receives only a checkout URL or QR code payload generated by the backend. This prevents API key exposure and ensures transaction validation on the server.

### 2.2 File Storage Separation
Large binary files (videos, PDFs, images) are stored in S3-compatible object storage. The database stores only metadata and reference URLs. This keeps the database lean and performant.

### 2.3 Isolated Payments Module
All money-related logic — checkout, refunds, revenue sharing, invoice generation — lives in a dedicated `payments` module. Gateway swaps (e.g., adding a new provider) should not require changes to course or grading logic.

### 2.4 Audit-First Mutations
All create, update, delete operations write an audit log entry capturing: user, action, entity, old values, new values, IP address, and user agent.

### 2.5 Role-Based Access Control (RBAC)
Three roles with distinct permissions:

| Permission | Student | Instructor | Admin |
|------------|---------|------------|-------|
| View published courses | Yes | Yes | Yes |
| Create/manage own courses | No | Yes | Yes |
| Manage all courses | No | No | Yes |
| Manage users | No | No | Yes |
| Manage categories | No | No | Yes |
| Grade submissions | No | Yes* | Yes |
| View admin dashboard | No | No | Yes |
| Configure system settings | No | No | Yes |

\* Instructor can grade their own course submissions only.

### 3.2 Key Design Decisions

**Soft Deletes vs Hard Deletes**
- Users and courses use hard deletes (with audit logs preserving history)
- Payments use status fields (`pending` → `completed` → `refunded`) rather than deletion

**JSON Columns for Flexibility**
- `prerequisites`, `learningOutcomes`, `attachments`, and `metadata` use PostgreSQL JSONB
- This allows schema evolution without migrations for loosely structured content

**Enumerated Types**
- `Role`: STUDENT, INSTRUCTOR, ADMIN
- `AccountStatus`: ACTIVE, INACTIVE, SUSPENDED, PENDING_VERIFICATION
- `CourseStatus`: DRAFT, PUBLISHED, ARCHIVED

**Indexes (Planned)**
- `users.email` — unique constraint (auto-index)
- `courses.slug` — unique constraint (auto-index)
- `courses.status + courses.categoryId` — composite for catalog queries
- `enrollments.userId + enrollments.courseId` — unique composite
- `audit_logs.entity + audit_logs.createdAt` — for report queries

## 4. API Design

### 4.1 Base URL
```
http://localhost:5000/api/v1
```

### 4.2 Response Format
All responses follow a consistent envelope:
```json
{
  "success": true,
  "data": { ... },
  "meta": {          // for list endpoints
    "page": 1,
    "limit": 10,
    "total": 100,
    "totalPages": 10
  }
}
```

Error responses:
```json
{
  "success": false,
  "message": "Error description",
  "stack": "..."     // development only
}
```

### 4.3 Authentication
- Access token: JWT in `Authorization: Bearer <token>` header
- Expiry: 7 days (configurable)
- Refresh token: 32-byte random string stored in database
- Refresh expiry: 30 days
- Token refresh endpoint: `POST /auth/refresh`

### 4.4 Rate Limiting
- 100 requests per IP per 15-minute window (public endpoints)
- Stricter limits applied per user ID for sensitive endpoints (payments, auth)

## 5. Security Architecture

### 5.1 Defense Layers

| Layer | Implementation |
|-------|---------------|
| Transport | HTTPS enforced (production) |
| Headers | Helmet.js for security headers |
| CORS | Restricted to known frontend origin |
| Rate Limiting | Express-rate-limit per IP |
| Auth | JWT with secure refresh rotation |
| Passwords | bcrypt, 12 rounds |
| Input | Zod schema validation on all inputs |
| SQL | Prisma ORM (parameterized queries) |
| Audit | Immutable audit log table |

### 5.2 Payment Security
- API keys stored in environment variables only
- Payment callbacks verified with gateway signatures
- Webhook endpoints idempotent (replay-safe)
- Refund operations require admin approval for amounts > threshold

## 6. Scalability Considerations

### 6.1 Database
- Read replicas for analytics/reporting queries
- Connection pooling via Prisma (default 10 connections)
- Partition audit_logs by year if volume grows

### 6.2 File Storage
- CDN delivery for all static assets (videos, PDFs, images)
- Signed URLs for private content (course videos for enrolled students only)
- Video streaming via range requests (HTTP 206)

### 6.3 Caching Strategy (Future)
- Redis for session store and rate limiting counters
- Cache course catalog pages (5-minute TTL)
- Cache user progress calculations (1-minute TTL)
